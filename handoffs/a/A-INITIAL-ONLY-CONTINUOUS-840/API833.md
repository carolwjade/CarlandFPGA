## Operator intent JSON

`operator_intent.json` requires `action`, `requested_speed_m_s` (finite 0..0.25),
`requested_paused` (bool), increasing `seq`, and `epoch` matching config world_epoch.
Legacy `world_epoch` is accepted instead; when both are present both must match.
Legacy `actual_board_action_performed`, if supplied, must be false. Intents are
read as intent only, never as actual board receipts.

| action | Effect |
| --- | --- |
| `start` | Before first APPLY reservation, sets initial request and initial pause state; after reservation, stores only next-run initial preference. |
| `set_initial_speed` | Changes the initial request only before first APPLY submission; afterward stores only next-run preference. |
| `next_initial_speed` | Stores only next-run preference, including if received early. |
| legacy `set_speed` | Same initial/next behavior as `set_initial_speed`; never an ongoing cap. |
| `pause` | Requests actual zero PWM independently of slider value. |
| `resume` | Clears explicit pause, invalidates previous advice and waits for fresh AI; no latch reset or next-preference consumption. |
| `stop` | Keeps the existing native-stop / real-board-stop terminal path. |

`requested_paused` in a speed-only intent does not change pause state. Values
carried by pause/resume/stop do not overwrite either initial preference. A legacy
`stop_latched` flag is honored only for a control intent, never for a speed update
classified as next-run storage. A repeated native pause indicator is edge-handled
so it does not undo a later explicit JSON resume.

## Initial speed and ongoing speed

`RunControl.initial_request` defaults to 0.1 m/s and is updated by the initial
start/set actions. At the first APPLY submission, `reserve_initial()` captures
it before queuing board IO. Slider changes during that in-flight APPLY can only
update `next_initial_preference`. `consume_initial()` latches the reserved value
when the actual APPLY result is consumed, even if its command was zero.

Before that consumption, AI requests and command mapping use the initial request
or its reservation. The original mapping still applies actual AI limits, downward
physical 1/80 m/s quantization and validated steering bounds. The latched value is
the requested initial preference, not a claim that the board achieved that exact
speed; actual measured PWM/native speed fields remain separate.

After the first actual APPLY, **every newly submitted AI request and mapping call
uses physical max 0.25 m/s**. Original AI profile cap 0.1 m/s, C3, risk, uncertainty,
entry steering, source age, pose applicability and physical guards remain. Initial
zero is not a pause latch: after a real zero APPLY, later AI may choose motion.
Explicit pause continues to command zero. Resume uses fresh AI, including its
possible zero decision; a waiting zero/keepalive does not acknowledge resume as
applied. No slider-driven held-command reduction branch remains.

After reservation, preference storage leaves current advice, desired command,
generation, pause and speed policy untouched. Existing identical-command
keepalives still use new real APPLY/COMMIT requests and actual 12-second grants.

Next-run preference lives in status and the Root-owned UI slider. A NEW RUN must
send its stored preference in its own fresh `start` intent; this controller never
reuses an old epoch or resets a current run to consume it.

## Status and acknowledgement semantics

The `DEEPEYE-CONTINUOUS-HOST-801-v1` ABI and original board/source/ai/operator
objects remain. Added flat status fields:

- `initial_request_m_s`, `reserved_initial_speed_m_s` (null before submission).
- `initial_speed_latched`, `latched_initial_speed_m_s` (null before consumption).
- `next_initial_speed_m_s`: slider/next-run preference, **never current speed cap**.
- `current_speed_source`: `awaiting_actual_board_apply`,
  `actual_pc_ai_and_board`, `explicit_pause_via_actual_board`, or
  `host_safety_guard_via_actual_board`; changed only upon actual accepted PWM.
- `operator_preference_ack_seq`: stored speed preference identity.
- `operator_control_ack_seq`: identity acknowledged through actual control.
- `operator_control_pending_seq`: latest control intent identity; compare with
  control acknowledgement and state for pending work.
- `operator_ack_kind`: `preference_storage` or `actual_control`.

For a next-run storage intent, `operator_state` and nested `operator.state` are
`next_initial_stored`, and `operator_ack_seq`/nested `operator.ack_seq` identify
that storage. **This is not a board APPLY acknowledgement.** Later actual APPLY
receipts acknowledge their captured control sequence, never a newer slider seq;
they leave the latest preference-storage acknowledgement distinct. Normal control
states retain `pending`/`applied`; actual-zero and requested-pause remain separate.
Root's UI should use `next_initial_speed_m_s` for the editable slider, measured
PWM/native speed for current motion, and the new acknowledgement kind/state.

## Display sharing violation

Only status publication calls `publish_display()`. It catches `PermissionError`
from that atomic display write, emits `display-publication-delayed` to the normal
critical host journal, and returns. No retry loop, sleep, generation change or
physical-request replay is introduced. The next ordinary display refresh tries
the latest visible data again. Journal errors still propagate. `RESULT.json` and
other critical writes remain strict atomic writes, outside this suppression.
